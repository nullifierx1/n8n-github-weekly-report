# Недельный отчёт GitHub

Практика 8 курса «Технологии ИИ в разработке ПО». Выберите понедельник, чтобы открыть сохранённую сводку за неделю по `nullifierx1/n8n-code-review-test`. Интерфейс показывает четыре счётчика, разбивки по типам и авторам созданных Issues и сравнение с предыдущей неделей. Даты считаются по UTC.

Фронтенд использует React, TypeScript, Vite и Tailwind CSS. Кнопка, поле, подпись, карточки и сообщения об ошибках взяты из библиотеки **shadcn/ui**. Цвета, шрифт и скругления заданы в [теме](src/style.css).

## Запуск

Требуются Node.js 22.12 или новее, npm и GNU Make. Визуальные эталоны проверяются отдельно для каждой платформы.

```bash
make all-setup
make demo
```

Команда `make all-setup` устанавливает зависимости и Chromium для Playwright. `make demo` запускает Vite на `127.0.0.1` в текущем терминале до `Ctrl+C`. Для сборки используйте `make build`. Список команд доступен через `make help`.

### Подключение n8n

1. Импортируйте [workflow](n8n/weekly-report-api.json) в n8n. В Webhook выберите Header Auth credential с полем `X-Report-Token`. Используйте проект n8n с доступом к существующей Data Table `weekly_issue_stats` (ID `TaNHNo4q6sAD9eY9`). В двух нодах чтения проверьте привязку к этой таблице.
2. Опубликуйте workflow и скопируйте **Production URL** из Webhook. Скопируйте `.env.example` в `.env.local`. Укажите URL и значение header credential.
3. Перезапустите Vite. Браузер обращается к `/api/weekly-report`, Vite проксирует запрос в n8n. Переменные с URL и credential остаются на сервере Vite. При размещении статической сборки настройте проксирование отдельно.

Этот workflow читает сохранённые строки по ключу `nullifierx1/n8n-code-review-test#YYYY-MM-DD`. Данные записывает существующая автоматизация практики 7.2. Сохранённая неделя с нулевыми показателями показывает карточки с нулями. При отсутствии строки интерфейс сообщает, что отчёта за выбранную неделю нет. [HTTP-контракт](spec.md#http).

### Проверка в учебном n8n

1. До проверки откройте Data Table и убедитесь, что есть строки за `2026-11-16` и `2026-11-09`. Выберите понедельник, ключа которого в таблице точно нет, например `2026-11-30`, если он свободен.
2. Выполните `make demo`. Используйте адрес, показанный Vite. В примерах ниже это `http://127.0.0.1:5173`.
3. Выполните запросы через Vite. Заголовок авторизации добавит прокси.

```bash
curl -i 'http://127.0.0.1:5173/api/weekly-report?weekStart=2026-11-16'
curl -i 'http://127.0.0.1:5173/api/weekly-report?weekStart=2026-11-09'
curl -i 'http://127.0.0.1:5173/api/weekly-report?weekStart=2026-11-30'
curl -i 'http://127.0.0.1:5173/api/weekly-report?weekStart=2026-11-17'
```

Ожидаются соответственно `200 success` со счётчиками сохранённой строки, `200 success` с четырьмя нулями, `200 empty` для отсутствующего ключа и `400 error` для вторника. Сравнение сверяется с предыдущей строкой и равно `null`, если её нет. Затем отправьте те же валидные даты через форму и сопоставьте видимые ответы с запусками в n8n Executions.

Реальный запрос из React за 16–22 ноября подтверждён Production Execution №7509. Остальные ручные сценарии и сведения об их подтверждении собраны отдельно. [Проверка в n8n](evidence/live-integration/README.md)

## Тесты

```bash
make check
make test-report
```

`make check` собирает приложение и запускает все клиентские тесты. Чтобы запустить только тесты, используйте `make test`. Playwright сам запускает Vite. После завершения тестов `make test-report` поднимает HTML-отчёт на `http://127.0.0.1:9324/`. Если браузер не открылся автоматически, откройте адрес вручную. Сервер отчёта останавливается по `Ctrl+C`. Для тестов webhook и credentials не нужны. Тесты проверяют форму, валидацию, загрузку и повторную отправку, сохранённую неделю с нулями, отсутствие записи, ошибку и повтор запроса, полный путь до отчёта и вид готового отчёта на двух размерах экрана. Для нулевой недели, отсутствующей записи и ошибки есть отдельные мобильные эталоны. Контрактные тесты выполняют экспортированный код нод на строках формата 7.2 и сверяют ответы с клиентскими фикстурами.

Пять Windows-эталонов и пять Linux-эталонов входят в репозиторий. Визуальные эталоны зависят от ОС, системного шрифта и версии Chromium. Инструкция ниже нужна для восстановления отсутствующих снимков. Для подготовки эталонов на Windows запускайте нативный Windows Node.js в каталоге на диске Windows. Проверить платформу можно через `node -p process.platform` — ожидается `win32`.

1. Выполните `make all-setup`.
2. Остановите Vite на порту 4173, если он уже запущен. Выполните `make visual-snapshots`, чтобы сгенерировать только отсутствующие эталоны текущей ОС. В PowerShell без Make используйте `npm.cmd test -- tests/visual.spec.ts --update-snapshots=missing` после `npm.cmd ci` и `npm.cmd exec -- playwright install chromium`.
3. Откройте все пять PNG из `tests/visual.spec.ts-snapshots/` с суффиксом своей ОС. Проверьте, что видны целые подписи, карточки и сообщения, а мобильный экран не переполняется по горизонтали. При дефекте исправьте его, прежде чем сохранять эталон.
4. Выполните `make check` в той же среде, затем `make test-report` для просмотра HTML-отчёта.

## Прототип и AI

[PDF-экспорт макета](prototype/weekly-report.pdf) можно открыть прямо на GitHub. В нём показаны семь состояний сценария и мобильный экран. [HTML-прототип](prototype/report.html) можно скачать и открыть в браузере. Переключатель внизу показывает все состояния, в том числе загрузку и ошибку. Прототип создан с помощью Codex, при доработке использован референс из каталога v0. [Shadcn Dashboard](https://v0.app/templates/Pf7lw1nypu5)

Сокращённые постановки, использованные в работе:

- **Прототип.** Сделать экран недельного отчёта и показать исходное состояние, ввод, загрузку, успех, пустые данные и ошибку. Уложить карточки в две колонки на узком экране.
- **Реализация.** Взять формы и карточки из shadcn/ui, перенести согласованные состояния в React и подключить запрос по JSON-контракту.
- **Тесты.** Воспроизвести основной путь и задержку через Playwright. Повторить отправку до ответа и посчитать запросы.

При переносе прототипа в код добавлены отдельные сообщения о валидации и данные сравнения рядом с соответствующими счётчиками. В тесте двойной отправки задержанный ответ удерживается до конца попыток отправки. Так проверка не зависит от случайной продолжительности запроса.
