# Практика 8. Интерфейс недельного отчёта GitHub

> Рабочий отчёт. Интерфейс и клиентские проверки готовы. Для защиты ещё нужен запуск с опубликованным webhook в учебном n8n.

Этапы взяты из лекции 8: задача, прототип, контекст для агента, реализация и проверка. [Лекция 8](https://github.com/nullifierx1/ITMOv2/blob/main/lections/lection_8_Al%20engineering%20tools.pdf)

## 1. Задача

В практике 7.2 недельная сводка приходила по почте. В этой практике сопровождающий репозитория может сам выбрать неделю и посмотреть сводку в браузере. Сценарий один: выбрать понедельник, нажать «Показать отчёт» и увидеть, сколько Issues и PR создали и закрыли или влили за семь дней. Для созданных Issues выводится разбивка по типам и авторам.

Выбрали тестовый репозиторий `nullifierx1/n8n-code-review-test`, чтобы на демонстрации проверить результат по двум известным неделям. [Тестовый репозиторий](https://github.com/nullifierx1/n8n-code-review-test) · [ТЗ практики](https://github.com/ai-course-avito/ITMOv2/tree/main/practices/practice_08)

## 2. Прототип и выбор дизайна

Первый [HTML-прототип](prototype/report.html) собрали в Codex. Запрос был на один экран с формой и четырьмя карточками. В прототипе можно переключить исходный экран, ввод, загрузку, успех, пустую неделю и ошибку. На узком экране карточки стоят в две колонки.

После просмотра первой версии сверили экран с Dashboard из каталога shadcn/ui. В этом примере основные числа сгруппированы в карточки, а изменение показателя видно рядом с числом. Для отчёта взяли этот приём: дельта выделена компактной меткой в каждой карточке, подпись и число выровнены по одному отступу. Форма остаётся над отчётом, разбивки идут ниже. Эти изменения внесли и в приложение, и в прототип. [Референс shadcn/ui Dashboard](https://ui.shadcn.com/examples/dashboard)

Это второй проход по дизайну. Первый вариант уже был в репозитории к моменту выбора референса.

## 3. Что передали агенту

Для реализации использовали прототип, [спецификацию формы](spec.md) и описанный там JSON-ответ. Макет задаёт расположение элементов. В спецификации отдельно прописано, что делать при пустой дате, дате посреди недели, задержке, повторном Enter и ошибке сервера.

| Этап | Суть запроса к Codex | Что доработали после первого варианта |
|---|---|---|
| Макет | Собрать отчёт и показать состояния одного сценария. | Вынесли сравнение в отдельные метки на карточках и сохранили его рядом с каждым числом. |
| Интерфейс | Переиспользовать элементы shadcn/ui, подключить запрос по контракту и обработать состояния. | Добавили ошибки рядом с полем и блокировку в обработчике формы на время запроса. |
| Тесты | Проверить, что после отправки виден отчёт, а повтор во время задержки не даёт ещё одного запроса. | Управляем задержкой из теста, проверяем число запросов и делаем снимки после наступления нужного состояния. |

## 4. Реализация

Фронтенд написан на React и TypeScript. Сборка и локальный запуск идут через Vite. Кнопка, поле даты, подпись, карточки и сообщение об ошибке используют компоненты shadcn/ui. Цвета и типографика заданы в [теме Tailwind](src/style.css).

При отправке браузер вызывает `/api/weekly-report?weekStart=…`. Vite проксирует запрос к n8n. [Веб-workflow](n8n/weekly-report-api.json) валидирует дату, получает статистику из GitHub Search API и отдаёт JSON. У него отдельный Webhook. Автоматизация 7.2 с почтой и расписанием продолжает работать самостоятельно.

Пока ответ ожидается, кнопка выключена и виден статус загрузки. Обработчик формы дополнительно проверяет, есть ли запрос в работе. При ошибке поле сохраняет выбранную дату и форму можно отправить снова. Сценарий проверен с клавиатуры, включая переход к полю и отправку через Enter.

## 5. Проверки по лекции

Playwright запускает Vite и подменяет ответы API. Проверки поведения охватывают ввод, валидацию, загрузку, пустые данные, 500 с повторной попыткой и путь до видимого отчёта. В тесте с задержкой ответ удерживается, пока браузер повторяет отправку. До снятия задержки тест проверяет, что запрос остался один.

В [визуальных тестах](tests/visual.spec.ts) используются четыре снимка приложения:

| Снимок | Размер окна |
|---|---|
| Готовый отчёт | 1000 × 900 |
| Готовый отчёт | 390 × 844 |
| Пустая неделя | 390 × 844 |
| Ошибка загрузки | 390 × 844 |

Размеры, локаль и часовой пояс заданы в Playwright. Ответы фиксированы, анимации при съёмке отключены. Снимки делаются на всю страницу, поэтому в мобильный эталон входят и разбивки ниже первого экрана. Baseline привязан к Chromium в Linux.

На предыдущей итерации временно увеличили заголовок и скрыли текст ошибки. Упал визуальный тест и тест поведения при ошибке. После возврата исходников оба прошли. Этот эксперимент показывает визуальное отличие и то, что проверка поведения ловит исчезнувшее сообщение. ## 6. Что проверено и что показать на защите

- Через GitHub Search API подтвердили 8 созданных Issues, 4 закрытых Issues, 7 созданных PR и 1 влитый PR за неделю 16–22 ноября. За 9–15 ноября получили четыре нуля. [Данные GitHub](evidence/github-data.json)
- Интерфейс проверили через локальную подмену webhook с этими данными. Сняли загрузку, пустой результат и ошибку. [Материалы проверки](evidence/README.md)
- На защите нужен отдельный прогон с опубликованным webhook. Выбрать обе недели в интерфейсе и показать соответствующие запуски в n8n Executions. Затем показать подмену ответа и визуальный diff в Playwright. [Настройка запуска](README.md#подключение-n8n)
